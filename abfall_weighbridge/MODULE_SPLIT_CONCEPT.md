# Weighbridge module split concept

## Goal

`abfall_weighbridge` should be a small, dependable weighing module. Capturing the
legally relevant terminal record must not depend on warehouse, sales, purchase,
or accounting functionality. Those concerns are optional integrations layered
on top of the completed weighing.

This document defines the proposed split. It intentionally does not move code;
the split should only be implemented after this boundary is accepted.

## Proposed addons

### `abfall_weighbridge`

The core addon owns only the device and weighing workflow:

- station identity and edge connection configuration;
- terminal and scale configuration, archive mode, parsing settings, and secret;
- signed challenge issue and consumption;
- immutable `RN` measurements, raw evidence, CRC, identity, replay, and signature
  verification;
- tickets with partner, product, physical direction, commercial role, first and
  second weighing, deductions, measured net, and payable weight;
- the weighing lifecycle `draft -> first_weighed -> completed`, plus
  `cancelled`;
- operator, manager, and station-administrator security groups;
- the capture-focused kiosk and base weigh-ticket report.

It should depend only on `mail`, `web`, and `product` (including the standard
unit-of-measure functionality). It must not contain warehouse configuration,
orders, pickings, invoices, billing profiles, or billing cron jobs.

### `abfall_weighbridge_stock`

Depends on `abfall_weighbridge` and `stock`. It owns:

- station warehouse, picking-type, and location configuration;
- payable-kg conversion through Odoo units of measure;
- picking and stock-move links;
- incoming and outgoing no-charge transfers;
- tracked-product validation, backorders, returns, and correction support;
- an independent stock processing state and retry information.

### `abfall_weighbridge_sale`

Depends on `abfall_weighbridge_stock` and `sale_stock`. It owns:

- sales order and order-line selection;
- eligibility and remaining-quantity validation;
- configurable over-delivery tolerance and manager approval;
- spot sales and standard sales-pricelist resolution;
- fulfillment through the delivery generated by the sales order.

### `abfall_weighbridge_purchase`

Depends on `abfall_weighbridge_stock` and `purchase_stock`. It owns:

- purchase order and order-line selection;
- eligibility and remaining-quantity validation;
- configurable over-delivery tolerance and manager approval;
- spot purchases and vendor-price resolution;
- fulfillment through the receipt generated by the purchase order.

### `abfall_weighbridge_billing`

Depends on the core, sale, purchase, and `account` addons. It owns:

- billing profiles and immediate/monthly modes;
- invoice and vendor-bill links;
- supported SO/PO invoice creation and posting;
- monthly grouping, daily scheduling, and retry idempotency;
- invoice-line-to-ticket traceability;
- fiscal position, tax, currency, payment-term, and invoice-address handling;
- accounting security and billing status.

One billing addon is preferable initially because the common grouping and retry
logic is substantial. It can later be divided into sale and purchase billing if
a real deployment needs only one direction.

### `abfall_weighbridge_full`

An optional code-free convenience addon can depend on all of the above. It gives
deployments a single install target without putting optional behavior back into
the core.

### Edge service

The Linux edge daemon is operationally independent from Odoo and should
ultimately live as a sibling service, for example
`services/abfall_weighbridge_edge`. It is not an Odoo addon dependency. Moving
it is part of the later implementation, not this concept step.

## Dependency direction

```text
abfall_weighbridge
        |
        +-- abfall_weighbridge_stock
                |
                +-- abfall_weighbridge_sale -----+
                |                                |
                +-- abfall_weighbridge_purchase -+-- abfall_weighbridge_billing

abfall_weighbridge_full -> all addons above
```

Dependencies only point away from the core. The core must never import, search
for, or call models that exist solely in an optional integration addon.

## Separate lifecycle states

The present combined `settlement_pending` and `settled` states mix certified
capture with downstream ERP processing. Replace them with independent states:

| Owner | State field | Values |
| --- | --- | --- |
| Core | `weighing_state` | `draft`, `first_weighed`, `completed`, `cancelled` |
| Stock | `stock_state` | `not_applicable`, `pending`, `processing`, `done`, `error`, `reversed` |
| Billing | `billing_state` | `not_applicable`, `pending`, `allocated_draft`, `posted`, `error`, `reversed` |

A valid second capture completes the core ticket even if an optional integration
later fails. Errors remain visible and retryable in the integration that owns
them; they do not invalidate or roll back terminal evidence.

## Extension contract

Integration addons extend `weighbridge.station` and `weighbridge.ticket` using
normal Odoo model inheritance. The contract should stay narrow:

- the core publishes that a ticket has become `completed`;
- integrations select completed tickets whose own state is pending;
- every processor is idempotent and records its document links and last error;
- processing occurs after the capture transaction, through an explicit second
  RPC and/or a retrying cron, so a stock or accounting exception cannot roll
  back an accepted measurement;
- no external queue addon is required;
- extension views inherit the core forms and kiosk UI;
- extension reports inherit the base ticket report to add order, stock, or
  accounting references.

The core kiosk therefore handles ticket entry and weighing only. Installed
addons add order selection, fulfillment, pricing, and billing panels. A refresh
always reconstructs the UI from persisted core and extension states.

## Feature ownership

| Feature | Owner |
| --- | --- |
| Station/terminal identity and edge health | Core |
| Challenges, signatures, CRC, replay protection | Core |
| Measurements, deductions, net/payable weight | Core |
| Capture kiosk and base weigh-ticket report | Core |
| Warehouse, locations, pickings, moves, UoM conversion | Stock |
| No-charge incoming/outgoing stock operations | Stock |
| SO/line, spot sale, pricelist, sales over-delivery | Sale |
| PO/line, spot purchase, vendor price, purchase over-delivery | Purchase |
| Profiles, invoices/bills, grouping, cron, posting | Billing |
| SysTec communication daemon and simulator | Standalone edge service |

## Migration approach

1. Freeze the current behavior with tests and assign every existing field,
   method, view, security rule, and data record to an owner from the table above.
2. Create the integration addons and move implementation behind `_inherit`
   extensions while preserving existing model, column, relation-table, and XML
   identifiers wherever possible.
3. Reduce the core manifest and remove its stock, sale, purchase, and account
   imports only after their replacements install successfully.
4. Map the old ticket state as follows:

   | Existing value | New `weighing_state` |
   | --- | --- |
   | `draft` | `draft` |
   | `first_weighed` | `first_weighed` |
   | `completed` | `completed` |
   | `settlement_pending` | `completed` |
   | `settled` | `completed` |
   | `cancelled` | `cancelled` |

   Populate stock and billing states from existing document links and errors.
5. Move menu entries, views, access rules, scheduled actions, and report
   additions to their owning addons. Move the accounting group to billing.
6. Keep old data until migration checks prove that every link and state was
   transferred. Do not drop columns as part of the initial split.
7. Move the edge service to its standalone location after addon paths and
   packaging references have been updated.
8. Port the accepted Odoo 19 structure to the 18 and 17 branches only after the
   split is stable.

## Verification matrix

Test these installations independently:

1. core only;
2. core plus stock;
3. core, stock, and sale;
4. core, stock, and purchase;
5. the full stack including billing;
6. upgrade from the current combined module with existing tickets and links.

The split is accepted when:

- the core installs without `stock`, `sale`, `purchase`, or `account`;
- a second measurement remains accepted when downstream processing fails;
- no optional-addon model is referenced by core Python, XML, JavaScript, or
  access-control data;
- installing or removing an integration cannot alter immutable measurements;
- each integration can report and retry its failures independently;
- order-linked processing still uses the order-generated picking, never a
  duplicate direct picking;
- all installation combinations and the upgrade path pass their tests.

## Decision requested before implementation

Approve or amend these boundaries, in particular:

- whether stock integration should be installed at every site or remain fully
  optional;
- whether one combined billing addon is acceptable;
- whether the edge service should move to `services/` in this repository.

After that decision, the code can be split incrementally without changing the
captured legal evidence or forcing accounting dependencies onto core-only sites.
